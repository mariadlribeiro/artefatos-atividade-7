## 2. Avaliação analítica

### 2.1 Estrutura e documentação
- **(D)** O README é extenso. Tem visão geral do pipeline em 7 etapas, estrutura do repositório, selos pretendidos, requisitos de SO/hardware/ferramentas com versões, instalação (apt + venv), uso com `sudo`, Docker, exemplo mínimo com saída esperada, descrição dos artefatos de saída, duas "Claims" com procedimento e resultado esperado, tabela de dispositivos avaliados, 15 hashes de referência, notas de reprodutibilidade (estrita vs. funcional/comparativa), plano de demonstração e considerações éticas.
- **(C)** O código tem cerca de 2.000 linhas em 5 arquivos:
  - `iot_id_fingerprint.py` (1.271 linhas): pipeline nmap/UPnP + SSDP → dumpcap → nping → p0f → tshark → canonização → SHA-256, mais um modo `--mode network`;
  - `canonicalize_features.py`: políticas `stable`/`rich` e `host_kind` iot/mobile;
  - `fingerprint_hash.py`;
  - `iot_net_scanner.py`;
  - `fingerprint_subnet.sh`.
- **(D)** `testes/FORMULA-FINGERPRINT.md` documenta formalmente a fórmula (`SHA-256(UTF-8(json.dumps(sort_keys, separators=(",",":"))))`) e quais campos entram em cada política. Há também um rascunho de artigo e um estudo de variáveis estáveis, em português.
- **(D/C)** Há inconsistências entre a documentação e o código:
  1. O README declara **Python 3.8+** e recomenda **Ubuntu 20.04** (Python 3.8). O código, porém, usa `set[str]`/`list[str]` (linha 633) e `str | None` (linha 656) em assinaturas, sem `from __future__ import annotations`. Na execução (seção 3.2) o pipeline falha em 3.8 e 3.9. O mínimo efetivo é Python 3.10.
  2. A saída esperada no README (`Starting Network Scanner...`, `DEVICE INVENTORY`, `Name:`) está em inglês, mas o código imprime em português (`Iniciando Scanner de Rede...`, `INVENTÁRIO DE DISPOSITIVOS`, `Nome:`).
  3. A Claim #1 manda `cd /fingerprint`, caminho que não existe no repositório. `fingerprint_subnet.sh` está versionado sem bit de execução (`100644`); o README instrui `chmod +x`.
  4. O exemplo mínimo do README mostra que o comando padrão (sem `--canon_policy`) gera `e20c4825…` com `name` e `server` no CANON_STRING. No código atual, a política padrão `stable` **exclui** `name` e `server` (ver 2.3).
  5. `__pycache__/` foi versionado com `bundle_snapshot.cpython-39.pyc`, de um módulo que não existe no repositório. Isso indica que o código evoluiu depois da geração dos resultados.
- **(D)** A licença aparece apenas no texto do README ("BSD License", © RNP, programa Hackers do Bem). Não há arquivo `LICENSE` e a variante da BSD não é especificada.
- **(D/C)** O `Dockerfile` (ubuntu:22.04, Python 3.10) e o `docker-compose.yml` (`network_mode: host`, `NET_ADMIN`/`NET_RAW`, volume `./runs`) são coerentes com a documentação. Porém, a imagem **não instala `sudo`**, e o código chama `sudo nmap` internamente (`nmap_upnp_scan`, `nmap_mobile_scan`), assim como `fingerprint_subnet.sh` (`sudo "$PYTHON"`). No contêiner, a etapa nmap/UPnP falharia em silêncio (exceção capturada → `{}`), e o orquestrador de sub-rede via Docker (documentado no README) falharia por falta de `sudo`. Isso foi verificado por emulação na seção 3.3 (item 9); o contêiner real não pôde ser construído.

### 2.2 Qualidade do código (C)
- A divisão em módulos é clara e há logging detalhado por etapa (`fingerprint_pipeline.log`), medição de tempo, argumentos de CLI documentados (`--help`), opção `--cleanup` e um fallback (p0f → tshark → TTL apenas).
- A ordenação de `LOCATION`s do SSDP para garantir determinismo (`_sorted_ssdp_locations`) mostra atenção à reprodutibilidade.
- Fragilidades observadas:
  - O parser do nmap usa `if "Name:" in line`, que também casa com `Model Name:`. Assim, `name` pode ser sobrescrito pelo modelo. Isso foi observado na execução do `iot_net_scanner.py` ("Nome: ModelB" para o dispositivo B) e afeta a política `rich`.
  - Se a canonização falhar, o processo termina com **código de saída 0** (a exceção é capturada e `main()` retorna `None`).
  - Há lógica UPnP/SSDP duplicada entre `iot_net_scanner.py` e `iot_id_fingerprint.py`.
  - Não há testes automatizados nem CI.
  - Comentários e mensagens misturam português e inglês.
- **Questão metodológica (C/A/E):** quando o alvo não responde com SYN+ACK e não há UPnP, o fallback gera o CANON_STRING degenerado `{"pcap_syn":{"ttl":"64"}}`. A SHA-256 desse texto é `5b60133e2971f571f7a4ceadd55041a78771b65189e64c0f891eb687ab37bc74`, que é **exatamente a hash de referência publicada para "IP Camera Model B"**. Essa hash, portanto, não identifica um dispositivo; representa apenas "TTL = 64", e qualquer host Linux/Android sem portas abertas na janela de captura colide com ela (confirmado em E, seção 3.3).

## 4. Conclusões por critério

### D — Disponibilidade
- **(D/E)** O repositório GitHub é público e foi clonado sem autenticação. Tem código completo, README detalhado, Dockerfile/compose e dados de teste. A licença (BSD, RNP) está declarada no README.
- Ressalvas: não há arquivo `LICENSE` nem variante BSD especificada (D); não há release/tag nem DOI/arquivamento permanente (Zenodo etc.), então o artefato depende só do GitHub (D); `__pycache__` está versionado (C).
- **Conclusão:** o critério de Disponibilidade é **atendido**, com as ressalvas de persistência e formalização da licença.

### F — Funcionalidade
- **(E)** Todos os componentes executaram com código de saída 0 em Python 3.13: scanner, pipeline (políticas stable e rich, `--cleanup`), orquestrador de sub-rede (incluindo `-r` e `--dry-run`) e CLIs de canonização/hash. Os artefatos documentados (`features_canon.json/.txt`, `fingerprint_sha256.txt`, `fingerprint_pipeline.log`, `fingerprint.json`, pcap) foram gerados com o formato e o conteúdo descritos. A estrutura do CANON_STRING segue a fórmula documentada.
- Falhas do artefato:
  - incompatibilidade com Python 3.8/3.9, apesar de declarada (E);
  - script sem bit de execução (mitigado pela instrução `chmod +x`) (E/D);
  - saída esperada do README não corresponde ao idioma do código (D);
  - imagem Docker sem `sudo`, apesar de o código e o orquestrador o chamarem (C, emulado em E);
  - código de saída 0 em caso de falha de hash (C).
- Limitações do ambiente: a imagem Docker não pôde ser construída (registro bloqueado); os testes usaram dispositivos sintéticos em vez de IoT físicos; as versões de nmap/tshark diferem um pouco das indicadas.
- **Conclusão:** o critério de Funcionalidade é **atendido com ressalvas**. O artefato executa e produz as saídas esperadas no caminho documentado (Linux, Python ≥ 3.10, sudo). As falhas encontradas são de documentação/compatibilidade e não impedem o uso.

### S — Sustentabilidade
- **(C/D)** Pontos positivos: código modular (coleta, canonização e hash separados e reutilizáveis via CLI), logging estruturado por etapa, parâmetros configuráveis, fórmula documentada em `FORMULA-FINGERPRINT.md`, Dockerfile, dependência Python mínima, README organizado e notas éticas.
- **(C/D)** Pontos negativos:
  - nenhum teste automatizado nem CI;
  - versões de dependências não fixadas e requisito de Python incorreto;
  - lógica duplicada entre scanner e pipeline;
  - bug de parsing `Name:`/`Model Name:`;
  - comentários, mensagens e documentos auxiliares misturando português e inglês;
  - os resultados armazenados não correspondem à versão atual do código (sem versionamento da política de canonização nem tag que associe resultados a código);
  - artefatos órfãos (`bundle_snapshot.pyc`).
- **Conclusão:** o critério de Sustentabilidade é **atendido com ressalvas**. A estrutura permite entender, manter e adaptar o código, mas faltam testes, versionamento de resultados e consistência entre código e documentação.

### R — Reprodutibilidade
Três níveis foram separados:
1. **Existência de resultados dos autores (A):** existem 22 execuções e 15 hashes de referência. Porém, dados brutos que sustentam as referências existem para apenas 4 das 15 linhas, e os PCAPs não foram incluídos. Por isso a cadeia captura → features não pode ser reauditada.
2. **Repetição dos resultados no próprio ambiente (E, offline):** aplicando o código atual aos bundles dos autores, a hash de referência é reproduzida para:
   - Samsung UN32J4303 na política padrão;
   - TCL Smart TV Pro apenas com `--canon_policy rich`, não documentado como necessário (o README sugere o comando padrão);
   - Xiaomi MiTV **em nenhuma política**, porque os resultados foram gerados por uma versão anterior da canonização que não está no repositório.

   A hash de "IP Camera Model B" é um fingerprint degenerado (TTL = 64). Os próprios dados dos autores mostram instabilidade para hosts sem UPnP (.3: 2/3; .100: 3 hashes diferentes em 3 execuções).
3. **Reconstrução independente (E):** em testbed sintético, as propriedades qualitativas das Claims foram reconstruídas:
   - mesma hash em execuções repetidas (determinismo);
   - mesma hash para "modelos idênticos" em IPs diferentes;
   - hashes diferentes para pilhas TCP idênticas com identidade L7 diferente (Claim #2);
   - hashes diferentes para pilhas diferentes.

   A execução também mostrou que dispositivos distintos sem UPnP e sem portas abertas colidem no fingerprint de TTL apenas. Isso limita a afirmação "different devices produce distinct fingerprints". A reprodução estrita das hashes é impossível sem o hardware e firmware originais, como os autores reconhecem (D). Isso é limitação de ambiente, não do artefato.
- **Conclusão:** o critério de Reprodutibilidade é **parcialmente atendido**. O modo "funcional e comparativo" proposto pelos autores foi reconstruído de forma independente com dispositivos sintéticos. A rastreabilidade entre o código atual e os resultados/hashes publicados não se sustenta (política padrão divergente, uma referência irreproduzível pelo código, uma referência degenerada, PCAPs e dados brutos ausentes para a maioria dos dispositivos).

## 6. Discussão das evidências

1. **Peso das evidências.** As conclusões de F e R se apoiam principalmente em execução independente (E) num testbed controlado. Esse testbed exercita todas as ferramentas reais do pipeline (nmap/upnp-info, SSDP, dumpcap, nping, p0f, tshark) contra pilhas TCP reais do kernel Linux e respondedores UPnP. Ele valida o **mecanismo**, mas não as **features de dispositivos IoT reais**: firmware, variação de SSDP e comportamento sob tráfego real ficam fora do teste. Os resultados armazenados pelos autores (A) foram usados só como referência para recomputação. Não foram tratados como execução independente.

2. **Falha do artefato vs. limitação do ambiente.**
   - **Falhas do artefato:** requisito de Python incorreto (3.8/3.9 quebram); política padrão do código diferente da que gerou as hashes publicadas; uma referência (Xiaomi) irreproduzível pelo código atual; imagem Docker sem `sudo`; script sem bit de execução; saída esperada desatualizada.
   - **Limitações do ambiente:** ausência dos dispositivos físicos; Docker Hub bloqueado; proxy HTTP que exigiu `NO_PROXY`; versões de nmap/tshark ligeiramente anteriores às indicadas.

3. **Validade das afirmações.** O determinismo é forte no nível do mecanismo: a canonização com chaves ordenadas e JSON minificado é determinística por construção (C) e foi estável em todas as execuções sintéticas (E). Ele depende, porém, de o alvo responder com SYN+ACK nas portas sondadas ou expor UPnP. Caso contrário, o fallback de TTL apenas produz um identificador não discriminante. Uma das 15 hashes publicadas é exatamente esse caso, e os dados dos autores mostram a variação entre execuções que isso provoca. A Claim #2 (resolução de colisão L3/L4 via L7) foi confirmada de forma independente.

4. **Rastreabilidade.** O ponto mais fraco para R é a falta de vínculo versionado entre código e resultados. Sanar isso exigiria: uma tag/release do código usado para gerar a tabela de referência, a indicação de qual política (`stable`/`rich`) a produziu, os bundles e PCAPs de todos os dispositivos da tabela e a correção do requisito de Python.
