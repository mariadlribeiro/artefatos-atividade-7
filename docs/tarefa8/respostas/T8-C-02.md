## 1. Resumo

1. **Disponibilidade:** o repositório é público e pode ser clonado de forma anônima. O README tem as seções esperadas pelo SBRC. Não há arquivo `LICENSE`, apenas uma seção no README que menciona "BSD License" sem indicar a variante. Também não há tag, release nem DOI. [D, E]
2. **Funcionalidade:** com Python 3.13, fiz a instalação nativa como descrita no README. Num laboratório L2 isolado, com dispositivos emulados, executei com código de saída 0 o scanner, o pipeline completo (nmap → dumpcap/nping → p0f → tshark → canonização → SHA-256), o orquestrador de sub-rede e as ferramentas offline. Todos os artefatos de saída documentados foram gerados. Ressalvas:
   - O script principal falha em Python 3.8 e 3.9, embora o README e o artigo indiquem "Python 3.8+" e "Ubuntu 20.04 ou superior".
   - Não foi possível construir a imagem Docker, porque o proxy bloqueia o Docker Hub (limitação do ambiente). A análise do Dockerfile indica que falta `sudo`. Numa simulação, o orquestrador falhou com código 127 e o estágio nmap foi pulado silenciosamente.
   - Várias saídas apresentadas no README não correspondem às do código atual. [D, C, E]
3. **Sustentabilidade:** a canonização e o hash estão em módulos separados, com CLIs próprias, e há logs por estágio. As reivindicações estão mapeadas no README. Ressalvas:
   - o arquivo principal é monolítico (1.271 linhas, com uma função de 383 linhas);
   - há código duplicado e exceções amplas engolidas silenciosamente;
   - o processo retorna código 0 mesmo quando falha;
   - não há testes automatizados;
   - parte dos documentos internos está desatualizada. [C, D, E]
4. **Reprodutibilidade:**
   - Sem os dispositivos físicos, a reprodução estrita da Tabela 5 não é possível (limitação do ambiente).
   - Independentemente do ambiente, o código publicado, com a política padrão, **não regenera** parte dos hashes publicados a partir dos próprios dados dos autores:
     - TCL Smart TV Pro: só com `--canon_policy rich` ou com um commit antigo;
     - Xiaomi: com nenhuma versão publicada;
     - impressora: o log é internamente inconsistente.
   - 7 dos 12 hashes distintos publicados não têm nenhum dado bruto no repositório.
   - No laboratório emulado, os comportamentos qualitativos foram observados: estabilidade entre execuções, distinção entre dispositivos, modelos idênticos com hash idêntico e desambiguação por L7.
   - Também apareceram as fronteiras desses comportamentos: o hash de hosts sem UPnP muda com o tráfego incidental, e o fingerprint publicado da "IP Camera Model B" é o hash genérico de "somente TTL=64", que reproduzi com um host emulado qualquer. [A, C, E, E sobre A]

### 2.3 Laboratório usado para a execução independente (criado pelo avaliador; não faz parte do artefato)

Como não havia dispositivos físicos, montei uma **LAN L2 isolada com namespaces de rede Linux** (`lab/lab_up.sh` e `lab/lab_down.sh`). O namespace raiz do host não foi alterado. A estrutura é:

- namespace `lan` com a bridge `br0`;
- namespace `ev` (10.77.0.2/24), que faz o papel da "máquina Linux na mesma LAN" do README e onde o artefato foi executado com as ferramentas do host;
- seis dispositivos emulados por `lab/emulator.py`, um script do avaliador que só usa a biblioteca padrão do Python. Ele responde a SSDP M-SEARCH (UDP 1900, grupo 239.255.255.250), publica um XML de descrição UPnP e abre portas TCP.

- não há tráfego de fundo real;
- a bridge se comporta como um switch, ou seja, o host de captura não vê o tráfego unicast entre terceiros.

Por isso, o laboratório testa a **mecânica** do artefato, não as afirmações empíricas sobre dispositivos reais.

*Tentativa preliminar:* montei primeiro o laboratório com contêineres Docker, usando uma imagem vazia criada localmente e `/usr` do host montado somente leitura. ### 3.3 Código

**Pontos positivos [C]:**

- **Serialização determinística:** `json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=False)`, com SHA-256 sobre UTF-8, conjuntos normalizados e ordenados, e LOCATIONs SSDP ordenados por porta, path e URL.
- **Canonização isolada:** a canonização (`build_canon`) fica em módulo próprio, com CLI (`canonicalize_features.py`, `fingerprint_hash.py`), o que permite recomputar hashes offline.
- **Rastreabilidade:** há um log estruturado por estágio (`fingerprint_pipeline.log`) e um bundle bruto (`fingerprint.json`) por execução.
- **Orquestrador:** `fingerprint_subnet.sh` usa `set -euo pipefail` e tem `--help`, `--dry-run`, `-r` e `--cleanup`.

## 8. Discussão das evidências

1. **Natureza das evidências.** As conclusões sobre funcionamento se apoiam em execuções minhas (E) das ferramentas reais (nmap, nping, dumpcap, p0f, tshark) contra pilhas TCP/IP reais do kernel Linux e serviços UPnP emulados. Os resultados armazenados pelos autores (A) não foram tratados como execução independente. Quando os processei com o código publicado (E sobre A), o objetivo foi verificar a consistência entre dados, código e artigo, e não reproduzir o experimento.

2. **Falha do artefato e limitação do ambiente.**
   - São limitações do ambiente:
     - a ausência dos 15 dispositivos;
     - o bloqueio do Docker Hub;
     - a instabilidade do daemon Docker;
     - as versões de ferramentas ligeiramente diferentes.
   - São falhas do artefato, porque independem do ambiente:
     - o `TypeError` em Python 3.8/3.9;
     - o código de saída 0 em falha;
     - o estágio `upnp-info` que nunca roda;
     - a captura de lixo no campo `server`;
     - a falta de `sudo` no Dockerfile, comprovada por análise e simulação (não por execução do contêiner);
     - sobretudo, a **deriva entre o código publicado e os hashes publicados**.
   - O caso TCL Smart TV Pro mostra a deriva com clareza. Os próprios bundles dos autores, processados pelo código atual com a política padrão, geram `3ce29174…`, e não o `e20c4825…` publicado. Logo, um avaliador com o mesmo televisor também não obteria o hash da tabela.

3. **Reprodutibilidade em três níveis.**
   - *Existência:* há resultados publicados, mas a base de dados que os sustenta é parcial (3 modelos com bundles, 2 com logs, 7 sem dados, nenhum PCAP).
   - *Repetição no ambiente do avaliador:* a integridade interna dos bundles é total (22/22) e o parser p0f é estável (22/22). Mas só 9/22 bundles regeneram o hash armazenado com a configuração documentada, e a tabela publicada mistura hashes calculados com pelo menos três variantes da canonização: a atual, "com `name`+`server`" e "com `name`". O log da impressora é inconsistente.
   - *Reconstrução independente:* o mecanismo descrito no artigo foi reconstruído e se comportou como anunciado para hosts com UPnP. Isso inclui a estabilidade, a distinção por L7 e a identidade de modelos iguais. Cinco hashes publicados sem dados foram reconstruídos exatamente a partir dos atributos publicados, o que reforça a coerência do formato canônico atual com parte da tabela.

4. **Alcance da afirmação de determinismo.**
   - O determinismo "por construção" é uma propriedade da função CANON → SHA-256, e foi confirmado.
   - O determinismo do *fingerprint de um dispositivo* depende de que as entradas coletadas sejam iguais. Os dados dos autores (.100 e .3) e o meu experimento E13b mostram que, para hosts sem UPnP, a presença de tráfego de saída visível no ponto de captura altera o hash.
   - Quando nenhum SYN ou SYN+ACK é observado, o fallback de TTL produz hashes genéricos. O `5b60133e…` aparece para uma câmera no artigo, para dois hosts não relacionados nos dados dos autores e para um host emulado qualquer no meu laboratório.
   - O artigo reconhece "low-entropy fingerprints" para esses casos. O README, porém, apresenta esses hashes como referências de identidade sem essa ressalva.

5. **O que reduziria as ressalvas** (sugestões, não critérios novos):
   - regenerar a tabela de referência com o código e a política publicados, ou documentar e fixar a política e o commit usados;
   - publicar os bundles ou PCAPs de todos os dispositivos da Tabela 5;
   - corrigir a compatibilidade com Python 3.8 (`from __future__ import annotations`) ou o requisito documentado;
   - instalar `sudo` no Dockerfile ou deixar de depender dele quando o processo já roda como root;
   - retornar código de erro em caso de falha;
   - corrigir o parser e o uso de `upnp-info` (incluir `-sU -p U:1900`);
   - incluir um arquivo LICENSE e uma release/DOI.
